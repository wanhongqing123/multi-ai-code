# 第三方命令行工具的进程内接入规范

本规范适用于**开源库自带命令行程序**、但 MaiChat 必须在 iOS、Android、macOS、Windows 等平台以共享核心提供其能力的场景。目标是复用上游命令的参数语义和执行代码：主模型调用一个命令工具，传入参数数组；宿主在进程内的工作线程调用经过改造的 argc/argv 入口，**不启动子进程**。

FFmpeg / FFprobe 是参照：[内嵌入口](../third_party/ffmpeg/fftools/mai_fftools_embed.h)、[模型工具](../AgentTools/MaiFfmpegTools.cpp)、[现状与限制](EmbeddedFfmpegTools.md)。curl 和 OpenSSL 已按此模式接入受限子集；实际支持范围以各模型工具的说明为准。

## 接入时先选这条路线

1. **先查该开源库是否提供 CLI。** 核对上游命令源文件、main(argc, argv)、子命令分发、参数解析、构建依赖及许可证；不能只看到系统安装了一个同名可执行文件就算源码里有可嵌入的 CLI。
2. **有 CLI 时，默认照 FFmpeg 做进程内改造。** 编译并复用上游的命令实现，把原本只供进程启动的 main 路径改成可反复调用、返回状态码的执行函数；Agent 工作线程传入 argc/argv 调用。工具层负责路径、权限、取消和结果适配，不为每个已有 CLI 子命令再手写一套不一致的算法。
3. **没有 CLI 时，才以库 API 设计类型化能力和模型工具。** 如果有 CLI，但完成必要的进程状态和退出路径改造后仍无法安全嵌入，要明确记录原因、可支持的范围和替代方案；不能用局部 API 包装冒充“上游完整 CLI 已接入”。

这是一条**默认工程路线**，不是“把可执行文件放进线程”或“把 main 改个名字”两个文本操作。FFmpeg 的嵌入版除了入口改名，还重置全局变量、处理进程退出路径、日志与取消，并串行执行；缺少其中任何一环，工作线程仍与整个 App 共用同一进程。FFmpeg 是架构参照，不代表现有工具已通过本规范每一条边界审计；concat 列表、滤镜中的间接文件引用仍需单独核查。

## 一、对外工具契约

1. **一个上游命令行程序对应一个模型工具。** 例如 ffmpeg、ffprobe 是两个程序，分别注册两个工具；OpenSSL 的 dgst、x509 等是同一个 openssl 程序的子命令，原则上从一个 openssl 工具进入。不要仅因新增子命令就新增一个模型工具。
2. 主参数为字符串数组 arguments，**不包含程序名**。工具层补入程序名和强制安全参数，再交给进程内执行入口。参数个数、单项长度和总长度必须有界；拒绝空项、NUL、解析失败和不支持的选项。
3. 工具说明与 Schema 只声明**实际接通并验证**的命令、参数及结果。保留上游语法是目标，不能因此宣称整个上游 CLI 都已可用。不能执行的子命令返回明确的 NotSupported，不降级为“看起来成功”的空结果。
4. 工具结果必须含真实的退出状态和必要的结构化产物引用；日志有上限且标明是否截断。只拿到半截 JSON、半个输出文件或一次启动结果，不算任务成功。
5. 对外工具名是协议的一部分；要改名时同步修改注册、主模型提示、权限判断、UI 展示、测试和工具清单。历史消息可以保留原记录，但不应把新旧名字同时暴露给模型，除非明确设计了迁移期。

示意：

~~~json
{"arguments":["-i","input.mp4","-frames:v","1","frame.png"]}
~~~

OpenSSL CLI 的已开放子集采用同样形状：

~~~json
{"arguments":["dgst","-sha256","photo.jpg"]}
{"arguments":["x509","-in","cert.pem","-noout","-text"]}
~~~

OpenSSL 工具目前仅接受只读的 `version`、`dgst`（限定算法和单个工作区文件）及 `x509`（限定只读输出选项和单个证书文件）。不会接受密钥、签名、网络或输出路径选项。

## 二、嵌入上游入口

1. 固定并校验第三方源码版本、许可和 SHA-256；从源码离线构建需要的静态库、命令实现及资源。各端共用一份命令逻辑，平台壳只负责界面、权限和必要的系统依赖。
2. 在受控桥接层暴露可调用入口，例如 mai_library_execute(argc, argv, context)，返回状态码。普通 main 可以作为改造起点，**不能只把 main 改名后在线程里调用**。
3. 审计入口和它能调到的子命令。所有可能触发 exit、_exit、abort、进程级信号处理、全局标准输入输出重定向及 atexit 的路径都必须处理：正常错误应返回状态，不能结束宿主 App。不能证明安全的子命令不得注册。
4. 每次调用前初始化、调用后清理并恢复命令级与库级可变状态。若上游使用进程级全局变量、日志回调、默认配置或 provider 状态，必须证明重复调用不会串状态；必要时用每库一把锁串行执行。**工作线程不提供进程隔离**，也不能阻止 exit() 结束整个 App。
5. 执行发生在 Agent 的阻塞工作线程或专用工作队列，绝不占用 UI 线程。已有工作线程时不必再额外创建一个线程；线程的职责是调度和取消，隔离仍靠安全改造、边界校验与串行化。
6. 取消和超时必须合作式生效：把 Agent 取消标志传入命令的中断检查，长循环定期检查。无法安全中止的命令不能对用户承诺“可取消”；不能用杀线程、longjmp 跨任意 C/C++ 栈帧或杀宿主进程代替取消。

## 三、输入、输出与权限

- 所有直接路径及**间接引用**都走 MaiFilePath、MaiFileSystem 与宿主访问边界。间接引用包括 concat 列表、配置文件、滤镜表达式、响应文件和子命令再次打开的素材。只检查 -i 和最后一个参数不够；无法解析并约束的引用形式要拒绝。
- 默认禁止交互式 stdin、覆盖已有文件和未经授权的网络协议。新产物使用工作区内的新路径，尽可能先写临时文件、验证后发布；源文件保持不变。需要覆盖或发送到网络时，按具体操作单独审批。
- 不能因工具名统一而统一放行权限。根据解析后的子命令及目标逐次判断：只读查询、文件修改、私钥生成、签名、网络发送是不同风险。密码、私钥及长期 Token 不进入模型参数、日志或聊天历史；需要时由宿主安全存储和原生交互提供。
- 捕获命令输出时优先使用库的 BIO、日志回调或专用 writer；不要在多线程 App 中用进程级 dup2 偷换 stdout/stderr。给模型的输出要有字节上限、截断标记和稳定错误码。
- 公开头只放中立的 C++ 类型，不暴露 JSON、Qt 或供应商 HTTP 类型。独立能力同时提供类型化直接入口与 MaiTool 入口，两者复用同一执行核心，遵守 [CodingStyle.md 第 14 节](CodingStyle.md)。

## 四、目录、注册与验收

| 内容 | 放置位置 |
|---|---|
| 上游源码、固定版本和必要补丁 | `MaiAgent/third_party/<library>/` |
| 中立的执行接口与工厂声明 | `MaiAgent/include/Mai<Library>Tools.h` 等同名头 |
| 参数、路径和审批适配；模型工具实现 | `MaiAgent/AgentTools/Mai<Library>Tools.cpp` |
| 平台构建与资源打包 | `MaiAgent/CMakeLists.txt`、各宿主构建脚本 |
| 直接 API、工具 API 和真引擎验证 | `MaiAgent/tests/` 及宿主集成测试 |

合并前至少验证：同一进程连续调用“成功→失败→成功”；不同会话并发请求的串行化；无效参数与越界路径；命令内部失败后 App 存活；日志/文件上限；取消后状态清理；真实文件产物；iOS、Android、macOS、Windows 的编译与可运行路径。没有覆盖的端或子命令只能标为未验证，不得宣称全平台可用。

## 五、当前实现范围

- `curl`：复用上游 CLI 源码，经参数适配后提供有界的 HTTP(S) 请求、上传和下载。协议、路径、配置文件和响应大小均受工具层限制。
- `openssl`：复用上游 `apps/openssl.c` 及 libapps/libssl。嵌入入口不再调用进程级 `exit` 或修改 SIGPIPE，BIO 在内存中收集；工具用互斥锁串行化，并只开放 `version`、`dgst`、`x509` 的只读子集。EVP/X509 类型化入口仍供程序内部复用。Mac 与移动端使用嵌入入口；Windows 目前仍保留原有类型化摘要和证书工具，尚未验证嵌入 CLI。
- OpenCV 上游的 `apps/` 是版本、标注、训练级联分类器等**分散的专用程序**，不存在覆盖边缘检测、轮廓、模板匹配和视频分析的通用 `opencv` CLI。因此现有 11 个 `cv_*` 工具继续通过 OpenCV API 执行；不能把它们说成 CLI 嵌入。若以后要开放上游某个独立 CLI，逐个按本规范审计和注册。
