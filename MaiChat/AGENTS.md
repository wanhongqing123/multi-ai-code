# MaiChat：按产品标准交付

MaiChat 是正在使用的产品，不是 Demo。这里的 iOS、Android 和桌面端改动都必须以真实用户完成一次任务的体验为验收对象。根目录 `AGENTS.md` 的通用要求同时适用。

## 开工前

- 先看现有页面、导航、状态和手势代码，并运行当前 App 看实际画面。不要凭描述猜控件位置、视图层级或系统转场。
- 用具体操作写清交互：从哪里进入；初始画面、触摸过程和完成后的画面；上一项/下一项的边界；加载、失败、取消、退出后回到哪里；键盘、旋转、后台恢复时会怎样。未想清这些状态时先不要写 UI。
- 优先复用当前产品的控件和视觉语言。新入口、菜单、模式只在确有用户价值时增加；把简单操作做成多步弹窗属于缺陷。

## 实现时

- 交互要有稳定的视图和数据生命周期。连续手势中的旧内容和新内容必须在同一容器中完成过渡；不要先销毁旧弹窗再创建新弹窗，然后用少量位移或透明度掩盖闪动。
- 图片、视频、缩放、拖动、播放进度等手势要明确划分优先级。切换内容不得意外重播当前视频、改变音量/倍速、丢失输入草稿或跨会话串内容。
- 用户能看见的加载中、空态、失败和完成态都要设计；出现失败时保留可恢复的上下文，不让界面停在空白或误导性的成功状态。
- 修改现有功能前先确认它在 IM、创作中心、横屏和其他共用入口的使用方式。修复一个入口不能破坏另一入口。

## 交付前：开发者自己实际验收

1. 按用户指定顺序：先运行 iOS 模拟器中的正常 App，录屏并逐段看进入、手势中、结束、退出；再构建、安装并启动真机版；最后运行 Android 模拟器中的正常 App。若某平台没有连接，明确标为未验证，不拿别的平台代替。
2. 使用本地测试账号和无需付费的素材走真实页面。涉及 IM 时用两个账号验证双方视角；涉及创作中心时检查多会话切换、最新消息位置、长列表与键盘；涉及媒体时检查连续浏览、缩放/拖动、播放控制和缺失文件。不得为验 UI 而触发付费模型任务。
3. 自动化断言和单元测试仅作补充。必须自己查看实际截图或录屏，特别检查闪帧、黑屏、布局跳动、错误层级、触摸区域和横竖屏切换。只看到“测试通过”不能宣称体验通过。
4. 交付说明要说清用户如何操作、屏幕上会看到什么、实际跑过哪些构建和设备、哪些路径尚未验证。不要把首次发现明显 UI 问题的工作留给用户。

## 已发生过的错误

- 2026-10-14：媒体左右滑动时先销毁旧预览、再创建新预览，只补 `48px` 位移和淡入；自动化能切换，真机看起来却一闪一闪。这种实现和仅凭功能断言验收的方式不得重复。正确验收条件是旧内容连续滑出、新内容同时滑入，过渡中没有空帧，并由开发者查看录屏确认。
