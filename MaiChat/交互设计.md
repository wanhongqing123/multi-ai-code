# MaiChat 交互设计

更新日期：2026-09-23

本文记录已确认的交互要求，作为实现、排查和验收的依据。当前重点是 iOS；涉及系统键盘及右滑返回的规则适用于 iOS。本文不代表现有代码已全部实现或通过验收。

## 1. 页面与区域名称

| 统一名称 | 含义 | 当前 iOS 代码入口 |
| --- | --- | --- |
| 消息列表页 | 显示各个会话、最近消息摘要和未读数 | `ConversationListView` |
| 聊天页 | 进入某个人的会话后，查看历史、输入及收发消息的整个页面 | `ChatDetailView` |
| 好友列表页（通讯录） | 查看、查找和管理好友 | `ContactsView` |
| 远程桌面页 | 查看及操作远端电脑 | `RemoteDesktopView` |
| 设置页 | 底部“我”入口中的设置 | `SettingsView` |

主业务按以上五个页面称呼。底部四个入口为“消息、通讯录、远程、我”；聊天页从消息列表页或好友列表页进入。另有登录页、图片／视频／文件预览页，以及搜索、添加好友等辅助界面或弹层。

聊天页内部统一称为：

- **顶部导航栏**：返回入口、当前聊天对象及相关操作。
- **消息展示区**：当前会话的消息内容及滚动区域。
- **输入区**：文字编辑框、语音入口、附件入口及发送操作。
- **系统键盘**：iOS 提供的屏幕键盘。

“消息列表页”与“聊天页的消息展示区”是两个不同概念。讨论问题时应明确页面和区域，避免统称为“消息界面”。

## 2. 主动定位最新消息的三种情况

仅以下三类普通聊天操作发起主动定位。

### 2.1 进入聊天页

用户从消息列表页或好友列表页选择某个人，进入其聊天页：

1. 确定本次进入的会话。
2. 读取或复用该会话最近 20 条消息；有更多历史时，按需加载。
3. 确定当前最新消息。
4. 数据和目标布局就绪后完成定位，使首屏显示最新位置。

再次进入同一个人的聊天页也适用。不能因为复用了页面或缓存而保留上次浏览历史的位置，也不能先展示历史位置、再明显跳到最新位置。

“最近 20 条”是初始读取及分页的约定，不是删除历史或把会话总消息数限制为 20 条。页面是否复用属于实现选择，不改变进入时定位最新消息的要求。

### 2.2 点击输入框、键盘展开

用户可能正在浏览历史，此时点击输入框准备聊天：

1. 确定当前最新消息。
2. 协调系统键盘、输入区与消息展示区的布局变化。
3. 消息定位与键盘展开同步发生，视觉上是一段连续动作。

不能先把键盘完整弹出，再补一次消息跳转；也不能让消息提前跳走，留下明显空白，再等键盘追上。

这里的“布局就绪”指目标位置已可正确计算，不是等待键盘动画结束。该触发对应键盘展开，不是每输入一个字都重新定位。

### 2.3 自己发送新消息

用户点击发送，包括发送语音转文字结果：

1. 创建新消息并加入本地会话列表，显示发送中状态。
2. 新消息行的数据和布局就绪后，立即定位到这条新消息。
3. 网络发送结果只更新发送状态，不再触发第二次定位。

定位不能等待服务器回执。网络较慢时，用户也应立即看到自己刚发送的消息。文本及附件使用同一原则。

## 3. 其他情况保持浏览位置

下列情况不主动跳到最新消息：

- 收到对方的新消息，尤其是用户正在浏览历史时。
- 加载更早的历史消息。
- 收到发送成功或失败的回执。
- 键盘收起。
- 输入内容增减导致输入框高度变化。
- 图片、视频或文件预览关闭后返回聊天页。
- 右滑返回被取消。

保持位置的含义是：用户正在看的消息及其相对位置保持稳定。内容重新排版时，仅保存一个旧的滚动偏移数值，未必能满足这一要求。

搜索结果、引用消息等由用户明确指定目标的导航，应定位到对应目标，不应被普通聊天的“定位最新消息”覆盖。

## 4. 右滑返回与键盘联动

聊天页支持从屏幕任意位置开始向右滑动返回，返回过程跟随手势。

**键盘展开时，聊天页退场与键盘收起必须同步发生，视觉上是一段连续动作。**

- 不能等键盘完全收起后才开始退页。
- 不能让聊天页已经退出一半，键盘仍独立留在原处。
- 手势完成后回到上一页，键盘不残留，上一页及底部导航栏正常显示。
- 手势取消时，聊天页恢复原位，保留消息浏览位置，不重新触发进入定位。
- 取消过程中的键盘状态也应与页面协调，不留下错位、空白或半退状态。

本节以“同时发生”为准，取代此前“先完整收起键盘，再开始退页”的描述。

## 5. 职责划分与事件处理

| 职责 | 负责事项 |
| --- | --- |
| 消息数据 | 会话选择、历史读取、消息新增、持久化与发送状态更新 |
| 内容渲染 | Markdown、附件等内容的排版与尺寸，不自行决定跳到最新消息 |
| 定位协调 | 统一接收三类定位请求，确认目标属于当前会话，并协调数据、布局与位置更新 |
| 键盘与输入区 | 输入、焦点、输入区高度及键盘布局变化 |
| 页面导航 | 进入、返回、手势完成和取消，以及离开页面后的请求失效 |

处理定位请求时必须保证：

1. 明确请求属于哪个会话、哪次页面进入、哪条目标消息。
2. 区分“消息已进入数据模型”和“目标消息已具备可用布局”。
3. 使用同一次更新中的有效数据，避免收到新消息 ID 后，又用旧消息数组检查并丢弃请求。
4. 一个操作对应一次定位意图；不能由焦点、键盘结束通知和网络回执分别补发重复跳转。
5. 页面离开后，旧回调不得再操作该页面或影响另一个会话。
6. 用户开始新的手动浏览后，过期请求不得把页面拉回旧目标。
7. 同一段键盘／返回交互统一协调，避免多套独立动画互相追赶。

## 6. 当前 iOS 组件说明

- **键盘**：系统键盘，应用负责唤起、收起及周边布局联动。
- **文字编辑框**：系统 `UITextView` 的子类 `GrowingComposerUITextView`，通过 SwiftUI 包装；自动增高、发送、语音长按及编辑菜单等逻辑由应用实现。
- **消息展示区**：SwiftUI `ScrollView` 与单一 `LazyVStack`。内部以最新消息作为滚动起点，并通过坐标变换保持视觉上的“旧消息在上、新消息在下”。消息不会在历史容器与尾部容器之间迁移；键盘改变可用高度时，最新位置自然贴着输入区。
- **普通消息 Markdown**：自定义代码拆分段落、标题、列表、代码块、表格等，再由 SwiftUI `Text`、`VStack` 等排版；行内样式使用系统 `AttributedString(markdown:)` 解析，并有渲染缓存。

系统组件负责基础能力，不代表自定义组合后的布局、定位、生命周期和性能已由系统保证。

## 7. 验证与修改顺序

先梳理事件、数据、布局、滚动和导航之间的完整顺序，建立复现用例，再修改代码。

至少覆盖：

- 首次进入、再次进入同一会话、切换不同会话。
- 在最新位置或历史位置打开键盘，检查动画全过程的同步情况。
- 键盘已展开时连续发送短消息和多行消息。
- 延迟网络回执，确认新消息在回执之前就显示并定位。
- 浏览历史时收到消息、加载历史及收到回执，确认不被拉走。
- 键盘展开时右滑返回，包括完成、取消和快速松手。
- 长 Markdown、不同消息长度及较多历史消息下的位置稳定性和性能。

验收不能只检查编译成功、滚动方法被调用或最终位置正确。还必须检查中间帧、实际可见位置、重复触发、过期回调和性能。

## 8. 当前状态与边界

本轮已完成代码修改及模拟器验证，尚未安装到真机验证。修复结论限定于本文涉及的消息定位、键盘联动和返回交互。

已通过实际页面日志确认过一处漏触发：定位回调收到新的消息 ID，但检查的是旧消息数组，导致提前退出。现改为读取当前数据模型并校验会话。列表采用统一的布局容器和底部起点，避免依赖尚在变化的历史总高度定位。

本轮验证包括：

- 实际聊天页加载更早历史、再次进入同一会话。
- 浏览历史时插入新消息，所观察消息的位置前后保持一致。
- 打开键盘、右滑返回及重新进入后打开键盘。
- 连续发送短消息和多行消息；在模拟回执延迟 20 秒时，新消息仍在回执前可见。
- 组件级检查可用高度变化时的底部对齐、历史追加位置保持、返回取消及过期定位请求失效。

加载历史可在滚动到最早已加载消息时触发，也可使用“加载更早消息”入口。历史加载完成后不额外执行跳转。

模拟发送和消息注入仅存在于独立测试副本，不进入正式应用代码。

此前的文字重叠、白屏和内存异常没有因本文或局部交互测试而获得“已解决”的结论。

## 9. 主线程与后台任务边界

- 主线程负责控件更新、焦点、导航动画、布局，以及发布用于显示的状态；不能等待文件、数据库、解析或音频操作同步完成。
- SQLite 历史读取与写入由历史持久化 actor 执行。一次最近页或更早页读完后，在后台完成 Markdown 准备，再校验会话和加载代次，交给页面。
- Markdown 块解析、行内样式解析、表格宽度分析、会话摘要在后台解析队列执行。页面使用已准备好的内容，不能在 `body` 或视图初始化中执行解析。
- 文件读取、复制、校验、图片编码及落盘在文件队列执行；媒体可用性检查独立使用元数据队列，避免排在大文件读写后。
- 音频会话配置、录音、播放器准备，以及语音 SDK 的创建、启动、停止、取消与释放，由同一个带 RunLoop 的后台音频线程顺序执行。UI 仅发布录音、识别、发送状态。
- 移到后台不改变发送目标：任务启动时固定账号和收件人，完成后核对有效性。取消或切换账号后，不得把旧结果发布到新页面。
- 主动定位仍只采用第 2 节的三类事件；解析完成、附件检查、网络回执本身不新增定位事件。

线程审计及验证记录见 [iOS主线程审计](iOS主线程审计.md)。后台迁移不能替代对主线程停顿的运行时验证。

## 10. 临时输入与机器活动状态

适用：Multi-AI Code 内置 IM、Desktop MaiChat、iOS MaiChat。类型按操作来源判断，不能按应用或账号判断；Multi-AI Code 的手动 IM 输入同样属于人工输入。

- 人工输入采用三点呼吸气泡，不显示文字。
- AICLI 活动采用环形脉冲，配“思考中…”、“正在使用工具…”、“等待确认…”或“正在执行…”等短标签。标签由客户端按枚举生成，不传工具参数、命令、路径和推理内容。
- 状态显示在下一条回复的位置。正文入站并准备好展示时，在同一次界面更新中移除状态并显示正文。状态不增加聊天记录、未读、通知或最近会话摘要；浏览历史时不为状态更新主动跳到底部。
- 状态变化更新同一活动占位；收到正文后关闭该活动，下一个执行阶段使用新的活动 ID。任务完成只结束活动显示，不结束既有的 IM 回复转发订阅。
- 人工每次编辑刷新本地输入意图；四秒没有编辑、失焦、切会话、发送、关闭页面即停止。非空草稿本身不代表持续输入。

线格式为腾讯 IM 在线自定义消息：`namespace=multi-ai-code-activity`、`version=1`，带 `activityId`、递增 `sequence`、`kind`、`active`、`ttlMs`。五种 kind 为 `human-typing`、`machine-working`、`machine-thinking`、`machine-tool`、`machine-waiting`。三端均在普通消息入库和 AICLI 输入路由之前分流。

每条状态默认有效十二秒；机器任务仍活跃时宿主每五秒续期，人工持续编辑时至多每三秒发送一次。续期仅更新过期时间，不重建消息列表。停止和正文会记录短期结束标记，迟到的旧状态不能复活气泡；旧活动的停止包不能取消新活动的过期计时。离线状态不补发，断线、进程退出、账号切换和联系人权限撤销负责清理。

在线消息能力依据：[腾讯 IM 在线消息文档](https://cloud.tencent.com/document/product/269/75341)。当前 Codex IM 正文按完整 message item 转发；活动气泡在 IM 实际收到该条正文时替换，不意味着 IM 已改成逐 token 传输。

Android 对应实现与线程职责见 [Android 与 iOS 功能对齐](Android与iOS功能对齐.md)。


## 移动端 AI 助手

AI 助手是独立页签，使用 MaiAgent 核心和现有 IM Markdown 样式。模型、权限、会话、流式回复、工具结果与停止操作见 [AI 助手移动端接入](AI助手移动端接入.md)。回复增长时跟随底部；用户主动滑动查看历史时保留位置，点击发送或回到底部恢复跟随。
