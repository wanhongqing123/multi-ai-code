# iOS AI 助手连续查看视频帧后模型流超时（2026-10-01）

## 现场与复现

- iPhone 截图显示任务“查看剩下四个视频的画面”，四次 `view_image` 均标为完成，
  整轮耗时 977 秒，随后出现 `model stream inactive for 120 seconds`。
- 截图没有显示四次调用的文件路径、文件尺寸、请求体大小、模型服务端响应时间，
  也没有显示手机当前安装包的提交号。不能仅凭截图断言是哪一张图片或哪个网络环节故障。

## 定点证据

- 基线 `4b88b816` 的 `view_image` 允许单张 20 MB 原图，并把原路径存为工具图片结果。
  `MaiContextBuilder` 将每张工具图片作为后续模型请求中的多模态观察；
  `MaiOpenAiClient` 每轮都重新读取、Base64 编码这些历史图片。四张 4 MB 图片
  在最后一轮可形成二十多 MB 的请求体，之前几轮也会重复编码上传。
- 超时计时器原先从请求开始到收到模型正文/推理/工具调用持续计时，
  上传大请求期间也可能触发。旧错误只给 120 秒，没有请求字节数、图片数、
  响应字节数，不足以判断是上传慢还是服务端静默。

## 修复与验证

- MaiChat 的 `view_image` 用进程内 FFmpeg 生成最长边 1280 像素、最多 2 MB 的
  JPEG 模型预览，保留原文件。预览放在 Agent 工作目录供后续轮次读取。
- 对旧会话中已经保存的大图，模型请求层也会按同一规则生成预览并在客户端
  生命周期内缓存；文件未变化的连续轮次不重复生成。小图仍按原格式发送。
- 上传进度只在字节数实际增加时刷新空闲计时；若超时，错误包含请求字节数、
  图片数量和已收到的响应字节数，不记录图片内容或密钥。
- 模拟服务端用四张各 3 MB 的历史图连续请求两次，验证每张预览只生成一次、
  最后一轮线上请求体小于 3 KB；Mac 的真实 FFmpeg 测试验证 1920×1080 PNG 被转为不超过
  1280×1280、2 MB 的 JPEG。目标平台构建与回归结果在提交前核对。

## 未验证边界

- 尚未取得截图对应会话的四张原图及服务端日志，因此不能证明那次 120 秒
  超时完全由大图片引起；服务端拥堵或网络中断仍可能独立出现。
- 用户手机上仍需安装含修复的构建，旧包不会自动获得这项改变。
