# Cloud-drive video waits for a full download before playback (2026-10-26)

## User report and reproducible baseline

On iOS, Android or Desktop, open **My Cloud Drive** and select a video that is not already present in a local preview. The current code obtains a private OSS read link, downloads the complete object to a UUID-named temporary file, and only then opens FFplay. Close the preview and open the same video again: it downloads the complete object again. A 2 GB video therefore cannot show its first frame until the full transfer and local temporary storage are available. Upload resume does not provide playback streaming.

The user requested video-on-demand behavior: fetch the byte ranges needed for the first frame and subsequent playback, request a new range after seeking, and avoid materializing the entire source at its original or temporary file path. Images may keep their existing preview download path. Ordinary UI and Agent media-open actions must use one shared implementation.

## Evidence and constraints

- iOS: `MaiCloudDriveView.open` awaits `MaiCloudDriveClient.downloadForPreview` before creating `MaiFfplayVideoScreen(path:)`; closing removes the temporary file. Android: `MaiCloudDriveDialog.open` awaits `MaiChatAttachmentDownload` before `openCloudDriveVideo(path)`. Desktop: `CloudDriveDialog.startPlayback` awaits `mai_download_file` before `play_(target)`. FFplay currently opens its filename through `avformat_open_input` without custom AVIO.
- Cloud-drive play links are private OSS HTTPS GET signatures valid for **60 seconds**. The user account service signs links and does not proxy media bytes. Playback must obtain a new signature for requests after expiry without restarting the video or retaining account bearer credentials in the OSS request.
- A disposable canary account's synthetic 1,683-byte MP4 was uploaded to the dedicated OSS bucket and removed after a live Range probe. `bytes=0-0`, `100-199`, and the last byte returned HTTP 206, exact `Content-Range` and payload, with a stable ETag. An out-of-range request returned HTTP **200 with the whole object**, so a range reader must reject 200 rather than accidentally download the full video. After deleting only the probe object, the account list was empty, its play link returned 404, and its old signed OSS link returned 404. No user object was touched.
- The first *shared C++ API* production OSS canary on a 1,683-byte video failed: initial Range `0-1048575` exceeded the known object end, and OSS returned HTTP 200/full body. The source then correctly rejected the 200, but could not play a small video. The range-end calculation was changed to cap at the size already provided by the account play link; local TLS tests now deliberately return 200 when a requested end exceeds EOF. Independent production retest passed: the 1,683-byte video opened with 206 and its first/last 64 bytes matched. A 3,811,969-byte video opened with 206; reading its last 64 bytes triggered a second 206 instead of downloading the middle. Cache use after the tail read was 1,714,817 bytes. Both newly created disposable objects were deleted and verified absent; the canary account list was empty and old read links returned 404.
- Production renewal was tested with another disposable 3,811,969-byte H.264 MP4: the shared API opened with 206 and returned correct first bytes, then kept the source alive for 70 seconds. The original signed URL returned 403, confirming expiry, while an uncached tail read through the same VOD source returned 206 and correct bytes after transparent account-owned re-signing. Cache after this read was 1,714,817 bytes. Only this canary object was deleted, and account/list/read-link cleanup was independently checked; no user media was accessed.
- The recently repaired iOS camera MOV uses FFplay native P010/BT.2020/HLG frames and a source AMVE probe to enable EDR. A VOD input must preserve this route; treating a stream placeholder as an ordinary local path would silently fall back to SDR.

## Acceptance checks

1. Start playback after only the necessary small ranges, with bounded memory and no full local video file. Verify a MOV whose metadata is at the end of the object as well as an MP4 with metadata at the start.
2. Seek to an uncached point and verify the next request targets that byte range instead of downloading all intervening bytes. Exercise pause, resume, replay and speed changes after the 60-second signature expiry.
3. Require HTTP 206, exact `Content-Range` start/end/total and returned byte count; reject an ignored Range (HTTP 200), changed total/ETag, unsafe redirects, invalid sizes and requests beyond the 2 GB video limit.
4. On close, cancellation, account switch and network failure, stop reads, release the bounded cache and keep the playback position or an understandable error. No credentials or signed URLs in logs or files.
5. Keep images, explicit user-requested save/share and existing local-video playback working. Agent and manual cloud-video entry points use the same VOD source. iOS HDR/HDR rotation retains native P010/HLG/EDR playback on the supplied original MOV.

## Implemented path and verification (in progress)

- `MaiChat/Network/MaiCloudVod` uses shared libcurl for 1 MiB HTTPS Range windows, at most eight cached windows in memory, a 2 GB source limit, TLS/proxy settings and cancellation. One easy handle is reused for the session so successive ranges can share a live TLS connection; a local HTTPS fixture observed one connection across more than ten separate Range reads. It obtains and renews the 60-second private read link through the existing account API. It never writes an implicit playback file. The read callback requires HTTP 206, exact range/length/total and a stable ETag; a returned HTTP 200 is rejected before retaining a response body. URLs are restricted to the expected OSS host suffix and are not passed to FFplay argv or logging.
- Shared FFplay uses a seekable custom AVIO context backed by that source. Its read and `AVSEEK_SIZE` callbacks let FFmpeg fetch a MOV index from the tail and request later byte positions on seek. The iOS native HLG/AMVE preflight uses the same custom AVIO; otherwise cloud playback would lose the recently repaired P010/EDR route.
- Synchronous player shutdown formerly risked blocking the UI for a 90-second Range request. A restart-safe read interrupt now aborts the active Range or signed-link renewal without destroying the source, so replay and speed changes can reopen FFplay. A separate permanent cancel handles close and account switch. Local TLS tests cover blocked Range/renewal interrupt followed by another successful read of the same source.
- Shared local TLS tests passed for Range validation, random seek near a virtual 1.9 GB end, 403 renewal, changed ETag, ignored Range HTTP 200, cancellation and the 8 MiB cache bound. A Mac hosted FFplay end-to-end test played a 27,908,499-byte MOV whose `moov` is at the end: the first drawn frame required only 3,791,251 transferred bytes and four Range requests. Seeking to 11 seconds increased the request count from four to twelve and drew a later frame. Closing completed and the cache remained at most 8 MiB.
- Mac `cloud_drive_dialog_local_tls` and `cloud_drive_agent_tools_local_tls` both passed against the real Qt UI/Agent adapters.
