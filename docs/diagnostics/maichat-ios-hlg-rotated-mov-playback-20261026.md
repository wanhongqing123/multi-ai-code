# iOS HDR MOV playback fails before the first frame (2026-10-26)

## Report and reproduction boundary

- User device: iPhone 14 Pro Max. In the app's video player, one camera MOV opens to a black/nonresponsive picture; two same-scene MOV files play. The user later supplied the original failing file. The exact user entry point, on-device build and device log remain unverified.
- Supplied original: 18,452,323 bytes, SHA-256 `0d5c2ac9f84d9502ec489f7e34398aaae1ac2aae800941a814ba59e47ee7be14`. Local `ffprobe` confirms QuickTime MOV, HEVC Main 10 `hvc1`, `yuv420p10le`, 1920×1080, 16.505 s, BT.2020/HLG, Dolby Vision profile 8 with HLG compatibility, a −180° display matrix, AAC stereo, and five `mebx` data streams. The original stays outside the repository and was not edited or uploaded.
- Source tree inspected at `8ac971d3104ae447f965e8fb6ea0c0d479e4f248` with local changes. An earlier synthetic 128×128 HEVC Main 10/HLG/180° MOV under `/tmp/maichat-hlg-rotation-probe-20261026` was only a preliminary probe, not the reproduction below.

## Code evidence

- `MaiChat/ios/MaiChat/MaiChat/Media/MaiFfplayIosBridge.cpp` selects the native VideoToolbox/Graphics renderer for local HEVC Main 10 HLG without subtitle streams. A Dolby Vision/HLG camera MOV matches that selector if the local download retained the reported metadata.
- Shared `MaiChat/Media/ffplay.c` injects `hflip` and `vflip` for a −180° display matrix when automatic rotation is on. It selects best video/audio/subtitle streams; it does not open `mebx` data streams for playback.
- When the video filter graph fails before a frame, `ffplay.c` sends `FF_QUIT_EVENT`; its `do_exit()` returns status 0. The old iOS bridge retried the ordinary renderer only for nonzero exit status with zero presented frames. Therefore a zero-status, zero-frame native failure silently suppressed the fallback. The original-file simulator run below proves that this MOV hits that filter failure in the current iOS media stack.
- Apple documents Dolby Vision profile 8.4/HLG Main 10 playback on iPhone 12 and later. Existing `MaiChat/Media/FFPLAY_PARITY.md` records a successful iPhone 14 Pro Max HDR Main 10/Dolby Vision profile 8 sample. The codec combination alone is insufficient to explain the failure.

## Fix and verification

- The iOS bridge now falls back whenever the native attempt exits without a presented frame, regardless of its exit code. If neither route presents a frame, it returns an error instead of appearing to complete normally.
- A frame is counted only after the graphics presenter accepts it for its render queue. The ordinary software RGBA callback now counts successful frame submissions too; otherwise a video that actually displayed through the fallback would be mislabeled as a zero-frame failure. An accepted submission does not prove that Metal drew that frame; timed screenshots provide the visible-result check below.
- UI and Agent close mark the session as stopping before sending the command. Stop keeps requesting close until the worker finishes, covering the interval when FFplay resets its SDL event queue for the fallback run.
- `MaiChat/Media/tests/MaiFfplayIosBridgeFallbackTests.cpp` uses stub FFplay and graphics functions. Against the pre-fix bridge, it fails with `zero-frame native attempt did not fall back to software` (exit 1). Against the new bridge, it passes (exit 0): zero-code zero-frame retry, rejected native presentation followed by software retry, ordinary software RGBA presentation counted as success, native first-frame success, both routes zero-frame error, UI close and Agent close without retry.
- Targeted test command from repository root: `clang++ -std=c++17 -Wall -Wextra -Werror -pthread MaiChat/Media/tests/MaiFfplayIosBridgeFallbackTests.cpp MaiChat/ios/MaiChat/MaiChat/Media/MaiFfplayIosBridge.cpp -o /tmp/MaiFfplayIosBridgeFallbackTests && /tmp/MaiFfplayIosBridgeFallbackTests`.
- The changed bridge compiles for arm64 iOS Simulator with `xcrun --sdk iphonesimulator clang++ -std=c++17 -arch arm64 -mios-simulator-version-min=16.0 -Wall -Wextra -Werror -fsyntax-only ...`. Full-app and original-file simulator verification is recorded below.

## Native HDR rotation repair gate (2026-10-26)

The bridge's zero-frame fallback prevents a silent black result, but the fallback loses the P010/BT.2020/HLG frame path. The shared FFplay filter graph now inserts `hwdownload` followed by a `format` filter using `frame->hw_frames_ctx->sw_format` before the auto-rotation filters when a VideoToolbox frame needs rotation. This keeps the FFplay clock, decoder and ordinary unrotated path unchanged.

`MaiChat/Media/tests/run_rotated_hdr_playback_test.py` generates a 192×108 HEVC Main 10, BT.2020/HLG MOV with a −180° display matrix in a temporary directory. It checks the codec, color metadata and matrix with `ffprobe`, builds a C++ driver against the **real Mac hosted FFplay library** and the iOS bridge, and runs three cases: unrotated HDR, rotated HDR and ordinary SDR. The driver requires a non-flat video frame, zero `Impossible to convert between the formats` errors, and P010/BT.2020/HLG output from the HDR cases. It accepts `--original <path>` to read the private user MOV in place; no user media is copied into the repository.

Before rebuilding the FFplay library, the generated rotated case failed as expected: `presented=1 non_flat=1 hdr=0 p010_bt2020_hlg=0 filter_link_errors=1` (exit 6). The frame came from the bridge's software fallback. After rebuilding `maichat_ffplay_hosted` from the filter repair, the cases reported:

| Case | Non-flat frame | P010/BT.2020/HLG frame | Filter link errors |
| --- | ---: | ---: | ---: |
| Generated unrotated HDR | 1 | 1 | 0 |
| Generated −180° HDR | 1 | 1 | 0 |
| Generated SDR | 1 | 0 | 0 |
| Supplied original MOV, read in place | 1 | 1 | 0 |

Targeted command, from the repository root, after building the Mac hosted library:

```sh
cmake --build MaiChat/desktop/build-release --target maichat_ffplay_hosted -j4
python3 MaiChat/Media/tests/run_rotated_hdr_playback_test.py \
  --library MaiChat/desktop/build-release/libmaichat_ffplay_hosted.dylib

This gate proves that the shared FFplay/bridge path submitted a non-flat P010/BT.2020/HLG frame to the host; it does **not** prove that Metal drew that frame on the actual iPhone screen. The simulator/phone UI, color appearance, playback continuity and rotation orientation require separate visual checks.

- A separate erased iOS 26.5 simulator ran a newly built App containing temporary timing probes in both the iOS bridge and `MaiGraphicsPresenter`. Before installation, `strings` confirmed the probes were present in the actual `MaiChat.debug.dylib`; the original test-bundle MOV had the same SHA-256 stated above. - The first P010 frame entered the Presenter at monotonic time 581604446 ms. The graphics thread started `format_conversion.effect` compilation at 581604466 ms and finished at 581612769 ms: **8,303 ms**. FFplay continued submitting frames meanwhile; frame 200 was queued at 581611083 ms. The first actual render ended successfully at 581614591 ms, **10,145 ms** after it started. Already queued frames 2, 3, 100, 200 and 300 were then skipped because a newer generation had arrived. This directly explains the advancing playback clock with black video on first use. ## iPhone 124 playback color compared with Photos (2026-10-26)

After installing the signed 124 build, the user confirmed that the original MOV now plays on the iPhone 14 Pro Max, but its color appears washed out compared with the original recording in Photos. This is a separate report from the rotation/filter failure. The supplied original remains outside the repository; no variant was substituted for this color investigation. The source baseline for this section is remote `main` at `d8470053` plus the local changes described below.

### Evidence and cause in the current pipeline

- `ffprobe` on the exact original reports HEVC Main 10, BT.2020/HLG, Dolby Vision profile 8 with RPU, and an **Ambient viewing environment** side record: 314 lux, x=0.3127, y=0.3290. This is the Apple camera's `amve` record. The new shared source probe reads the existing FFmpeg stream side data and encodes the corresponding eight-byte payload as `00 2f e9 a0 3d 13 40 42`; the original-file probe test passed.
- `MaiFfplayRendererBackend.cpp` transfers VideoToolbox's P010 frame and its basic color space/range/transfer flags. The previous `MaiVideoFrame` boundary had no AMVE or Dolby Vision per-frame output metadata. `MaiGraphicsPresenter.cpp` converted HLG with fixed 0.2 OOTF exponent and 1000/300 luminance scaling, then `default.effect` used fixed Reinhard tone mapping. `OBSSwapChain.swift` on iOS always used an 8-bit sRGB drawable and `metal-swapchain.swift` reset any iOS swapchain to SDR. Thus the 124 build compressed the HLG base image into SDR and did not use the source's viewing-environment metadata. The narrow P010 shader introduced for startup speed was pixel-identical to the full effect at the tested final frame; it did not change this color path.
- Apple's [TN3145 HDR video metadata](https://developer.apple.com/documentation/technotes/tn3145-hdr-video-metadata) explains the camera `amve` record and says omitting it can produce extra-bright imagery. Apple's [HLG EDR API](https://developer.apple.com/documentation/quartzcore/caedrmetadata/hlg%28ambientviewingenvironment%3A%29) expects an 8-byte big-endian `amve` payload; the installed iPhoneOS SDK header specifies that an HLG FP16 layer receives scene-referred inverse-OETF output in the nominal 0–12 range, while the system applies the display OOTF. This provides a concrete explanation for why simply changing the rotation filter could restore video yet leave the color unlike Photos. It does not isolate how much of the remaining difference comes from Dolby Vision RPU processing.

### HLG EDR repair under verification

- The shared FFmpeg source probe keeps the existing native-frame eligibility decision and additionally extracts `amve` from `AV_PKT_DATA_AMBIENT_VIEWING_ENVIRONMENT`. The iOS FFplay bridge requests EDR only after it receives a P010/BT.2020/HLG frame. Its graphics task configures **that player's swapchain**, retaining FFplay for decode and timing. The iOS layer uses FP16, extended linear BT.2020, `wantsExtendedDynamicRangeContent`, and `CAEDRMetadata.hlg(ambientViewingEnvironment:)` when iOS 17 or later provides the record. iOS 16 uses generic HLG metadata. If EDR is unavailable, it keeps the previous SDR rendering path.
- The new P010 HLG effect pass applies only the inverse HLG OETF, scaling scene-linear BT.2020 to the nominal 0–12 range; it omits the fixed exponent/luminance scale and Reinhard draw pass. The existing SDR and PQ paths remain on their previous shaders. Native-to-software fallback, a subsequent RGBA frame, and closing an HLG session all return the same swapchain to SDR before another frame is submitted.
- The existing bridge fallback test now covers HLG selection, AMVE propagation, native failure to software SDR, HLG close then SDR on the same view, and native P010 then RGBA in one run; the local C++ test passed. The Mac hosted FFplay gate passed for generated straight and rotated HLG, SDR, and the exact original: non-flat native P010/BT.2020/HLG frames with no filter-link errors. The compiled original-file gate explicitly asserted `has_ambient=1` and exact payload `00 2f e9 a0 3d 13 40 42`, independently of `ffprobe`'s text output. An iOS Simulator Debug build compiled successfully, and the exact original displayed upright video in the mixed-gallery test route; private screenshots `/private/tmp/maichat-ios-edr-audit/t02.png` and `t06.png` show the moving picture, with video-region RGB mean absolute difference 35.088. The simulator's `CAEDRMetadata.isAvailable` returned false and logged `HLG EDR unavailable; using SDR output`; these screenshots therefore **do not** verify EDR color.
- The reference inverse HLG OETF gives scene-linear 0.5→1.000000, 0.75→3.179551 and 1.0→12.000000. A Mac M3 Pro Metal offscreen probe rendered the new effect into FP16 and then through `default.effect`'s plain `Draw`: HLG code 768 produced 3.191406 in both textures versus 3.191443 expected, an FP16 rounding difference. Values above 1 were preserved, with no extra sRGB conversion. This proves the GPU conversion and draw math on Mac, not the iPhone's final display mapping.
- Signed iOS Release **2.2.3 (125)** built successfully. `codesign --verify --deep --strict` passed on the app and the IPA ZIP integrity check passed. The development-signed package is `MaiChat/ios/MaiChat/dist-hlg-edr-v125/MaiChat-iOS-2.2.3-125-HLG-EDR-dev.ipa`, 263,126,673 bytes, SHA-256 `b26491c55e3dccb05613f72c49da23f640cf7a82fbd81f6743f04e67f7046537`; its app executable SHA-256 is `3382d9f027182c19cc9994d2f99b922f4573518c7b1cf441b3401a59cf225c82`. The executable extracted from the IPA has the same SHA-256 as the app copy and the signed build output. The signed App was cover-installed on the iPhone 14 Pro Max: device readback shows version 125, the App launches, and the three pre-existing top-level App data entries remained in place.
- To test the exact supplied MOV without altering the user's account or installed App, a separate development-signed Debug 125 App with bundle ID `com.kongshang.maichat.hlgprobe` was installed. The MOV copied into only that App's container had the same 18,452,323 bytes and SHA-256 `0d5c2ac9f84d9502ec489f7e34398aaae1ac2aae800941a814ba59e47ee7be14`. Launching its existing local video-tool test route produced `[FFplayFrame] 1920x1080 format=4 colorspace=2 range=0` and `[MaiVideoHDR] HLG EDR enabled ambient=1` on the real iPhone. Thus the exact original reaches the P010/BT.2020 native route and iOS reports that per-view EDR with AMVE was enabled. This runtime log does not establish visual color parity with Photos. A direct `idevicescreenshot` attempt failed with `screenshotr Invalid service`; visual capture remains in progress.

**Remaining boundary:** The signed 125 App has been installed and launched, and the exact original enabled EDR in an isolated Debug 125 App on the same iPhone. The same clip still needs a visual comparison between MaiChat and Photos at matched playback time and screen brightness; neither the simulator SDR fallback nor an EDR-enabled runtime log can replace that observation. The HLG EDR path consumes `amve` but does not apply Dolby Vision RPU dynamic metadata, so exact Photos parity remains unproven. Do not treat the 124 playback-success observation as color acceptance.
